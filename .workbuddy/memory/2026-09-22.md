### M2 踩坑（重要，容易再犯）
1. **`XML_PARSE_NOBLANKS` 会删掉纯空白文本节点** → `<include>` 前后缩进消失，拼出 `SELECTid, user_nameFROM`。
   解法：不用 NOBLANKS，norm_text 把空白折叠成单空格（两端各保留一个），最后用 `sql_tidy()` 收尾（引号内空白不动，否则 `'a  b'` 会被改坏）。
2. **expr.c 释放了不属于自己的内存**：字符串字面量 `malloc` 出来的和 jansson 内部 `json_string_value()` 的指针混在一起 `free`。给 `ev_t` 加 `own_str` 标记，只在自己 malloc 时释放。
3. **关键字没词边界**：`and` 吃掉 `android`、`or` 吃掉 `order`。match_kw 要判断下一个字符不是 alnum/_。
4. **数组/对象被判成 null**：`<if test="list != null">` 对数组恒不成立。from_json 要补数组/对象 = 非空即真。
5. **foreach 每项带多余空白** → `( ? , ? , ? )`。每项单独渲染到临时 buffer 再 tidy。
6. `db.h` 公共头文件没带 `q/core/types.h`，却返回 `Q_OK/Q_ERR_*`，调用方得自己猜 —— 已补。
7. mock 驱动 `insert_id` 回填早于自增；mock 保存的参数指针在 mapper `build_free()` 后悬空 —— 都要拷进自己的静态池。

### M3 踩坑（重要）
1. **libcurl 默认继承 `http_proxy` 环境变量**（这台机器有 `http_proxy=http://127.0.0.1:49939`）。
   现象极具迷惑性：**第一次请求成功，之后全部 404** —— 因为 `curl_easy_reset()` 会把代理恢复成「读环境变量」，
   后续请求走了代理，请求行变成绝对 URI，对端路由匹配不上。
   解法：`q_httpc_new()` 和每次 `q_httpc_do()` 的 reset 之后都显式 `CURLOPT_PROXY=""` + `CURLOPT_NOPROXY="*"`。
   **内网服务间调用走代理本身就是错的，这条应该是客户端默认值。**
2. **路由按下标顺序匹配**：`/user/:id` 会吃掉 `/user/search`，静态路径必须先注册。后续应改成按精确度排序。
3. 可选驱动要用 CMake `if(TARGET q_db_mysql)` + `target_compile_definitions(... Q_HAVE_MYSQL)` 包起来，
   否则没装 connector-c 的机器链接直接失败。

## 对比分析：c_gateway_libuv_llhttp（另一个项目）

用户另一个项目 `/Users/mac/work/c_gateway_libuv_llhttp`（也是 unix2005 名下），要求与 qboot 对比。
**结论：两者不是同类，是分层关系，不该二选一。**

- 它 = **API 网关**（流量入口）：libuv + llhttp + libcurl + cJSON，反向代理 + 健康检查 + 轮询 + Prometheus + tracing。src/ 12 个 .c 共 3679 行 + gateway.h 860 行。
- qboot = **业务服务开发框架**（写服务的那层）：XML 外置 SQL + DB 抽象 + Consul。
- **唯一真正重叠**：它自带的 `sdk/`（libcservice，1035 行，cservice.h 只有 7 个核心 API）↔ qboot 的 libq_http + libq_reg。
- 类比：Spring Cloud Gateway vs Spring Boot。

### 它的硬伤（已核实，带行号）
1. **HTTPS 实际不可用（致命）**：入站密文 `BIO_write(ctx->ssl_bio,...)`（network.c:633）经 `bio_write` 写进 **ssl_write_buffer**（network.c:391-400）；而 `SSL_read` 走 `bio_read` 读的是 **ssl_read_buffer**（network.c:361-368），该 buffer **全仓库从未被写入**。握手不可能完成。加上 network.c:625-630 握手未完成时把 TLS ClientHello 当明文喂 llhttp。
2. **服务配置加载被注释**：main.c:285-289 整个 `load_service_config("services.json")` 在 `/* */` 里 → 启动后注册表为空，只能靠运行时 POST /services/register，且无持久化，重启即丢。
3. **性能数据无支撑**：README 的 1915 RPS / 5.2ms 仓库内无任何压测脚本或原始数据；且那是 curl_easy 阻塞版（旧 commit）的数字，异步化重构（curl_multi + uv_poll，async_http.c:185-189）后未重测。
4. **llhttp_execute 返回值全部忽略**（network.c:165/168/628/652），解析失败不回 400。
5. 请求体 `realloc` 无上限（network.c:91），DoS 面；内存池溢出兜底的 malloc 永不 free（utils.c:5-20）。
6. **零 C 单元测试**；Makefile 单条 gcc 直链，`sdk/` 与 `service_worker/` 不参与主构建；`src/consul.c`（19 行）是死文件；sdk/src 里 .o 混在源码目录。

### 它比 qboot 强的地方
- Prometheus 指标 + W3C Trace Context 分布式追踪（qboot 完全没有）
- HTTPS 方向对（虽坏了）
- libcservice 的 API 设计干净：init + route + run 三个 API 就能起一个服务

### 建议路线（已提给用户，等他拍板）
网关保留做流量入口（或换成 nginx），服务框架二选一收口到 qboot；
把它的 Prometheus/tracing 移植进 qboot 补短板。
